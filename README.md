# ETL Data Automation Pipeline

[![CI](https://github.com/sreejavuyyala/etl-data-automation-pipeline/actions/workflows/ci.yml/badge.svg)](https://github.com/sreejavuyyala/etl-data-automation-pipeline/actions/workflows/ci.yml)
[![Live dashboard](https://img.shields.io/badge/dashboard-live-2a78d6)](https://sreejavuyyala.github.io/etl-data-automation-pipeline/)
[![License: MIT](https://img.shields.io/badge/license-MIT-informational)](LICENSE)

**[View the measured-results dashboard →](https://sreejavuyyala.github.io/etl-data-automation-pipeline/)**

Scheduled, self-validating ETL from an OLTP sales system into a reporting
warehouse — built on **Azure Data Factory** and **SQL Server 2022**, using
Microsoft's **AdventureWorks2022** sample database as the source.

It replaces a manual export-and-load with a pipeline that moves only what
changed, checks its own work against the source, quarantines bad rows instead of
loading or dropping them, and raises an alert when something is wrong.

Everything reported below was measured on a live SQL Server 2022 instance
holding the real AdventureWorks dataset. Read
[`docs/metrics-methodology.md`](docs/metrics-methodology.md) for exactly what was
real, what was simulated, and which claims the evidence does not support.

## Architecture

```
   ┌────────────────────────┐
   │  AdventureWorks2022    │   Source OLTP system (read-only)
   │  Sales.SalesOrderHeader│   31,465 orders
   │  Sales.SalesOrderDetail│   121,317 order lines
   └───────────┬────────────┘
               │
    ①  Incremental extract  ── only rows changed since the last
               │               successful run, window [from, to)
               ▼
   ┌────────────────────────┐
   │  stg.*                 │   Landing zone — permissive by design, so a
   │  SalesOrderHeader      │   malformed row lands rather than crashing
   │  SalesOrderDetail      │   the extract
   └───────────┬────────────┘
               │
    ②  25 data-quality rules ── nulls, domains, contradictions, duplicates
               │
        ┌──────┴──────┐
      pass          fail ──────►  etl.etl_rejected_row
        │                         (full row as JSON + the rule that caught it)
        ▼
   ┌────────────────────────┐
   │  dw.*                  │   Reporting warehouse — constrained, indexed.
   │  SalesOrderHeader      │   MERGE upsert; nothing that failed a
   │  SalesOrderDetail      │   Critical check ever arrives here
   └───────────┬────────────┘
               │
    ③  Post-load validation ── row-count reconciliation, order totals,
               │               orphans, duplicates, pipeline lag
               ▼
        ┌──────┴──────┐
      clean         critical failure
        │              │
        ▼              ▼
   Advance the    ┌───────────────────────────────┐
   watermark      │  Logic App → email / Teams    │
                  │  Run marked Failed            │
                  │  Watermark HELD — nothing     │
                  │  is skipped, window re-read   │
                  └───────────────────────────────┘
```

**Orchestration.** Azure Data Factory: a schedule trigger at 02:00 UTC drives
`LoadSalesData_Pipeline`, which delegates to child pipelines for extract/load,
validation and alerting. The pipeline logic itself lives in SQL stored
procedures, so ADF calls the same code the local runner in `etl/` does.

## Measured results

From 9 completed runs against real AdventureWorks data. Generated by
`python -m etl.metrics`, which reads only what the pipeline recorded about
itself — full report in [`reports/metrics.md`](reports/metrics.md).

| | |
| --- | ---: |
| Runs completed | **9** |
| Runs completed with no human involvement | **88.9%** (8 of 9) |
| Rows extracted → loaded | **155,077 → 155,065** |
| Rows loaded as a share of rows extracted | **99.992%** |
| Rows quarantined (injected faults) | **12** |
| Validation checks executed | **324** |
| Check pass rate | **99.074%** |
| Row-count reconciliation pass rate | **100%** (36 of 36) |
| Unexplained row-count variance | **0** |
| Median run duration (incremental) | **0.45 s** |
| Initial full load (152,782 rows) | **73 s** |

The single failed run and the three failed checks were **deliberate**: 12
corrupted rows were injected to verify the validation layer. All 12 were
quarantined, none reached the warehouse, an alert was raised, and the watermark
was held so the next run re-read the same window and recovered without any
manual replay.

### What these numbers do not claim

There is **no measurement of the manual process this replaces** — no manual
export-and-load was performed or timed, so no "N% reduction in manual effort"
can honestly be derived, and none is reported. `etl/metrics.py` deliberately
produces no such figure.

"99.992% of extracted rows were loaded" is a completeness figure, not a semantic
accuracy figure. Verifying the latter would need a reference dataset to compare
against, and no such comparison was made.

**Azure Data Factory was never deployed.** The artifacts in `adf/` and the
templates in `infra/` are written against the documented schemas and 2024 API
versions, and they call the same stored procedures these measurements exercised
— but every run above was driven by the local runner in `etl/`, not by ADF.

**There is no SSIS in this project.** The scope permitted either SSIS or an
ADF-native build; this is ADF-native. No `.dtsx`, no SSIS Integration Runtime,
and no SSIS claim anywhere.

## Quick start

Needs Docker, Python 3.11+, and ~3 GB of disk.

```bash
git clone <this repo> && cd etl-data-automation-pipeline

cp .env.example .env
$EDITOR .env                          # set MSSQL_SA_PASSWORD

python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt       # needs ODBC Driver 18 — see docs/runbook.md

docker compose up -d                  # SQL Server 2022
./scripts/restore_adventureworks.sh   # downloads ~200 MB, restores, prints the baseline
./scripts/deploy_schema.sh            # creates SalesReportingDW and every object

python -m etl.run_pipeline --load-type Full    # first load: 152,782 rows
```

Then:

```bash
python -m etl.run_pipeline --trigger Scheduled   # incremental
pytest tests/ -q                                  # 41 integration tests
python -m etl.metrics                             # the measured report
```

**macOS note.** The ODBC driver install is the step most likely to stall: the
Homebrew formula checks `HOMEBREW_ACCEPT_EULA`, not the `ACCEPT_EULA` the
container image uses, and setting the wrong one leaves `brew` waiting on an
invisible prompt. See [`docs/runbook.md`](docs/runbook.md).

### Reproducing the measurements

```bash
./scripts/reset_warehouse.sh --yes
python scripts/run_experiment.py --nights 6 --fault-count 4
python -m etl.metrics --write
```

`run_experiment.py` asserts rather than reports: every source row accounted for,
injected faults quarantined, no faulty row in the warehouse, an alert raised,
the watermark held on failure, and the next run recovering unaided. It exits
non-zero if any of that fails.

## Design decisions

**The logic lives in the database.** Every stage — opening a run, applying rules,
loading, validating, deciding whether to alert — is a stored procedure. ADF
calls them; it implements none of them. This is what lets the local runner and
the cloud orchestrator execute identical code, and what makes the pipeline
testable on a laptop.

**Validation rules are data, not code.** The 25 pre-load rules live in
`etl.etl_validation_rule` and are executed by a generic engine. Adding a check
is an `INSERT`.

**Bad rows are quarantined, not dropped and not loaded.** A row failing a
Critical rule is copied to `etl.etl_rejected_row` — the whole row, as JSON, with
the rule that caught it — and removed from the batch. Inspectable and
replayable.

**The watermark advances only after validation passes.** This is the load-bearing
safety property. A failed run re-reads its window rather than skipping it, which
turns a failure from an incident into an inconvenience. Verified end to end.

**Reconciliation compares independently observed numbers.** The expected row
count comes from the *source*, on the source connection — not from what the
pipeline happened to receive. A check that compares a number against itself
always passes.

**Freshness measures pipeline lag, not data age.** The question is "has the
warehouse fallen behind the source?", not "is the data recent?". Measuring
against the wall clock would fail forever on a sample dataset whose newest order
is dated 2014, while saying nothing about whether the pipeline works.

**No credentials anywhere.** ADF reads its connection strings from Azure Key
Vault via managed identity. Locally, `.env` is gitignored. Nothing in this
repository can authenticate to anything.

## Repository layout

```
sql/
  00_restore_adventureworks.sql   Restore the source; MOVE clauses generated from the .bak
  01_create_databases.sql         Create SalesReportingDW
  02_target_schema.sql            stg / dw / etl schemas, control tables, reporting views
  03_etl_procedures.sql           Run lifecycle, watermarks, MERGE loaders
  04_validation_checks.sql        Rule table, rule engine, reconciliation, assertions

etl/                              Local runner — same stored procedures ADF calls
  config.py  db.py  entities.py  pipeline.py  alerting.py  metrics.py  run_pipeline.py

adf/
  pipeline/    LoadSalesData_Pipeline.json          Scheduled orchestrator (try/catch)
               LoadSalesData_Extract_Pipeline.json  Extract + load stage
               ValidateSalesData_Pipeline.json      Post-load validation
               RaiseAlert_Pipeline.json             Record + deliver an alert
  dataset/ linkedService/ trigger/                  Supporting artifacts
  alerts/      LogicApp_EtlFailureNotification.json Email + Teams fan-out
               AzureMonitor_PipelineFailedAlert.json Failure + silence detection

infra/main.bicep                  Azure SQL, Key Vault, data factory, RBAC
scripts/                          Setup, deployment, experiment and fault-injection harnesses
tests/                            41 integration tests against a live database
docs/                             architecture.md, runbook.md, metrics-methodology.md
  index.html                      The dashboard — served by GitHub Pages
reports/                          Generated metrics — regenerate, don't edit
```
