The incident

Deliberately induced, to prove the checks work

A data-quality layer that has never rejected anything is an untested claim. So twelve rows were corrupted at the source and the pipeline was left to find them.

RUN 8

Caught

Twelve corrupted headers extracted — orders due before they were placed, shipped before ordered, carrying negative freight. Three Critical rules fired, one per fault type. All twelve rows went to quarantine with the full row preserved as JSON and the rule that caught it.

RESPONSE

Held

The run was marked Failed and an alert was raised and delivered. Zero faulty rows reached the warehouse. Critically, the watermark was not advanced — so the window stayed unread rather than being stepped over.

RUN 9

Recovered

Once the source was repaired, the next scheduled run re-read the identical window and loaded all twelve rows. No replay was triggered, no backfill was scheduled and nothing was lost — the recovery is a property of the design, not an intervention.

What these numbers do not claim

Stated up front, because a dashboard is exactly where an unearned number would hide.

No manual-process baseline exists.
The manual export-and-load this replaces was never performed or timed, so no "reduced manual effort by N%" figure can honestly be derived — and none is reported. The metrics module has no code path that can produce one.
99.992% is completeness, not semantic accuracy.
It means every extracted row was either loaded or deliberately quarantined. Verifying semantic correctness would need a reference dataset to compare the warehouse against; no such comparison was made.
Azure Data Factory was never deployed.
The ADF pipelines, Logic App, Monitor rules and Bicep templates are written against the documented 2024 API versions and call the same stored procedures these runs exercised — but every measured run was driven by the local Python runner, not by ADF.
There is no SSIS here.
The scope permitted either SSIS or an ADF-native build. This is ADF-native: no .dtsx package, no SSIS Integration Runtime, and no SSIS claim anywhere in the repository.
Arrival patterns are simulated.
AdventureWorks is a static sample database, so order activity between runs was generated against the source and discovered by the pipeline through its own watermark. The rows are real rows that really moved; what is synthetic is the timing, not the processing.
